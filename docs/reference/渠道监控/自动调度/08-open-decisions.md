# 待拍板事项（自动调度，v2）

v1 只做冷却门 + 抖动重试 + 代 429 + 一行命令改上限，下面这些都不影响 v1。

## D1 用什么触发切换

```text
甲  拦截事件为主：60s 内某个用户被拦截到 N 次就切；TPM ≥ T 的重度用户只要拦截 1 次就切
乙  只看 TPM：用户流式 TPM ≥ T 就探测、就切
```

- 场景：按 LT 14:02 的数据（[07](07-lt-measurements.md)），乙要把 T 设到 59 万以下才会触发；可 13:48 那分钟 126 万完全正常，结果就是大量误切。甲只在真的被限流时才动。
- **建议：甲。**

## D2 别名谁来建

```text
手动：每加一条备用渠道，在面板上配一次别名和定价（04 第 3 节）
自动：hook 拿 channel:write + option:write 权限，自己建别名、写定价
```

- 场景：选自动的话，hook 一出 bug 就可能改坏渠道配置或定价。
- **建议：手动。** hook 只读写它自己的配置。

## D3 探测用的令牌权限

```text
channel:read     列渠道 / 启用的模型 / 重试次数
channel:operate  原生探测（同时也能启用、禁用渠道，刷新余额）
```

- 场景：令牌泄露后，别人能停掉你的渠道，但读不到任何渠道密钥。密钥要求 root、`channel` 密钥查看权限和二次验证。
- **建议：接受。** 有效期设 90 天，在 hook 配置文件里以 0600 权限保存。

## D4 按什么粒度区分用户

```text
令牌指纹：hook 直接能算出来；同一个用户有多个令牌时，每个令牌各自判断
用户 ID：要先把令牌对应到用户（需要额外的管理接口调用和缓存）
```

- 场景：一个用户开了 3 个令牌给 3 个 Codex 实例用。按令牌，3 个实例各自判断、各自切；按用户，3 个一起切。
- **建议：令牌指纹。** 实现最简单，粒度也更细。

## D5 先在 LT 上加一条备用渠道

- 场景：没有第二条同类型、能服务 gpt-6-astra 的渠道，探测、切换、摘除都没法测。
- **建议：** 先加一条（可以是另一个中转站），配好别名再开始 v2 的实测。
