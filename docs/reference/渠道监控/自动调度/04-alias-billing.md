# 别名模型：把普通用户送到指定渠道，并按新渠道计费

## 1. 为什么只能用别名

| 想做的事 | NewAPI 原生能不能做 | 依据（[01](01-newapi-native.md)） |
|---|---|---|
| 普通用户的请求指定走某条渠道 | 不能：只有管理员令牌可以 | `middleware/auth.go:704`、`:719` |
| 按渠道定价 | 没有这个功能，只按模型计费 | 全仓库没有按渠道定价的实现 |
| 外部写入亲和 | 没有接口 | 只有统计和清空 |

hook 的做法：把请求体里的 `model` 改写成**只有目标渠道才提供的别名**。之后选路和计费全由 NewAPI 原生完成：

- 选路：NewAPI 按（分组，别名）只能选到目标渠道。
- 计费：用当前用户自己的令牌、按别名的价格扣费，日志里记的是目标渠道。
- 按新渠道计费：别名可以单独定价，例如按这条渠道的成本价。

## 2. 别名命名规则

| 规则 | 原因 |
|---|---|
| 不能匹配任何亲和规则的 `model_regex`，出厂规则就是 `^gpt-.*$` 和 `^claude-.*$` | 一旦匹配，会查到这个会话原来绑在 A 上；A 不提供这个别名，严格模式下直接回 503（`service/channel_select.go:344`） |
| 推荐格式：`<短名>@ch<渠道ID>`，例如 `astra@ch12` | 一眼能看出是哪条渠道；按渠道拆分统计 |
| 每条渠道一个别名，不要几条渠道共用 | 共用的话，NewAPI 会在它们之间按权重随机选，hook 就控制不了去哪条 |

别名不命中亲和规则，所以 NewAPI 不会为别名请求记亲和。"按 TTL 一直用新渠道"完全由 hook 的路由表负责（[03](03-switch-algorithm.md)）。原渠道 A 上原有的亲和照常过期，互不干扰。

## 3. 每条备用渠道在面板上配一次

```text
渠道 #12（与 A 同类型，已启用，能服务 gpt-6-astra）
  模型：      增加 astra@ch12
  模型映射：  {"astra@ch12": "gpt-6-astra"}       ← 渠道 12 的上游收到的仍是真实模型名
  分组：      要覆盖所有会用 gpt-6-astra 的用户分组（hook 不知道某个用户属于哪个分组）
定价：        astra@ch12 = 渠道 12 的价格，或照搬 gpt-6-astra 的同一条 tiered_expr 表达式
令牌模型白名单：开了白名单的令牌要加上 astra@ch12
模型广场：    把别名隐藏掉
hook：        nahookctl set alias.12 astra@ch12
渠道 A 和其他渠道：都不动
```

没配别名的渠道，hook 能发现，但不会放进候选：没有别名就送不过去。

## 4. 考虑过但没采用的做法

| 做法 | 问题 |
|---|---|
| 用管理员令牌加 `sk-xxx-<id>` 指定渠道 | 费用记到管理员头上，不是当前用户 |
| 直接写 NewAPI 的 Redis 亲和键 | 依赖内部键格式，升级后可能失效；只对带 `prompt_cache_key` 的请求有效；LT 的 Redis 没对宿主机开放 |
| 用管理接口临时调渠道优先级或状态 | 全局生效，做不到按用户；还会改动面板 |
| hook 绕过 NewAPI 直接调上游 | 跳过了 NewAPI 的计费和日志 |
| hook 用 `channel:write` 和 `option:write` 自动建别名、写定价 | 权限过大，hook 出 bug 会改坏渠道和定价，见 [08](08-open-decisions.md) |

## 5. 别名带来的副作用

- 使用日志和账单里显示的是 `astra@ch12`。
- 别名需要单独定价，漏配会被 NewAPI 当作模型没有价格而拒绝请求（开了自用模式除外）。上线前要用测试令牌核对扣费。
- 别名请求的输出里，`model` 字段是上游返回的真实模型名，客户端一般不受影响。
